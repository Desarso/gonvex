## Summary
- **Batched sync resume**: Reconnect multiple active sync collections in a single network round-trip when the server supports batching
- **Warm query revalidation**: Avoid redundant payload transfer when resuming queries from cache by validating content hashes with the server
- **Sync mode optimization**: Support eager (full-collection) and progressive (key-based) resumption strategies for efficient sync recovery

## Changes
- **Faster reconnections**: When the server advertises `syncBatch: 1` capability, the client now groups sync open requests into a single `sync.openMany` message instead of sending them individually, significantly reducing reconnection time for apps with multiple live collections.
- **Smarter query caching**: Resumed queries now include a `cacheRevision` when subscribing. If the server confirms the cached result is still current (via content hash match), it sends a lightweight `query.progress` confirmation instead of the full result payload, saving bandwidth.
- **Optimized sync strategies**: The sync protocol now distinguishes "eager" mode (resume without row keys for full collection sync) from "progressive" mode (resume with specific row keys for partial updates), allowing the server to optimize data transfer based on collection characteristics.
- **Capability negotiation**: The server now advertises supported protocol features via the `capabilities` field in `session.ready` messages, enabling clients to adapt behavior dynamically (e.g., enabling batching).

## Technical Notes
- **Packages**: All packages (`@gonvex/client`, `@gonvex/protocol`, `@gonvex/react`, `@gonvex/cli`, `create-gonvex`) bumped to v0.1.16
- **Protocol**: Added `sync.openMany` and `sync.readyMany` message types; `query.subscribe` accepts optional `cacheRevision`; `sync.ready` includes optional `mode` field ("eager" | "progressive"); `session.ready` includes `capabilities` object with `syncBatch` version
- **Client**: Sync store schema updated to persist `mode`; query cache integration supports revision-based revalidation with 50ms fallback timer; supports up to 256 concurrent sync opens per batch
- **Server**: WebSocket handler processes batched sync opens; query cache revisions now include SHA-256 content hashes for validation; `syncClock` tracks `RetainedRevision` for efficient cursor validity checks without database queries
