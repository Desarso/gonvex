# Frontend Multitenancy

Generated bindings are project-level. A tenant is runtime context, not a
different generated API.

```tsx
import { GonvexClient, GonvexProvider } from "./gonvex/_generated/react";

const client = new GonvexClient(import.meta.env.VITE_GONVEX_WS_URL, {
  project: import.meta.env.VITE_GONVEX_PROJECT_ID,
});

export function App() {
  return <GonvexProvider client={client}>{/* app */}</GonvexProvider>;
}
```

The authenticated Account selects a tenant:

```ts
client.setAuth({ token, tenant: tenantId });
```

The runtime resolves the tenant database and checks the Account's active
tenant-local Member there. A client-provided tenant ID never grants access.

## Local Replica scope

The selected tenant, Account, Member, and visibility revision form the Local
Replica scope. Switching tenants creates a new scope and reconciles cached
entities, query memberships, pending commands, and cursor state before marking
the connection current. Components read through generated hooks; they should
not copy server data into React state or read the persistence adapter directly.

## Control Plane and tenant data

Use Control Plane operations for project identity, tenant discovery, Account
profile data, and membership routing. Use tenant-scoped Queries, Reducers,
Replica Collections, and Live Queries for business data. Application code never
connects directly to tenant databases or stores database URLs.

## Visibility

Visibility is declared once in the TypeScript module and enforced by Gonvex for
initial delivery, Live Query SQL, Replica Collection changes, and revocation.
The client can filter cached data for offline UX, but it is never the security
authority.
