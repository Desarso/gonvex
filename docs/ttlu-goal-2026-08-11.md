# Gonvex TTLU certification — 1,000-user Whagons workload

**Certification date:** 2026-08-12  
**Profile:** `tmp/whagons-1000-users-local.json`  
**Target:** 1,000 users, 1,700 WebSockets, 148,958 initial subscriptions, 2-minute ramp, 10-minute hold  
**Authoritative result:** `tmp/load-reports/whagons-1000-final.json`

## Executive verdict

The strict stretch goal of **p95 below 100ms** was **not achieved** in the required full simulation. The best stable, correctness-preserving certification reached:

- **182.68ms per-client p95**;
- **182.48ms time-to-last-user (across-commit) p95**;
- **187.23ms create p95**; and
- **178.32ms update p95**.

The run passed every operational and correctness gate observable by the harness: 1,700/1,700 connections, 148,958/148,958 initial results, zero setup/subscription/mutation errors, zero unexpected closes, no runner abort, and 99.06% of requested mutation throughput. Overall and per-path p95s are below the **200ms product ceiling**.

After 38 measured iterations, the remaining full-scale tail is a workload-size-dependent database/result-construction/fanout floor. It is not a fixed debounce, rerun-queue, GC stop-the-world, or generator saturation problem. Crossing 100ms from here would require a more fundamental application data/projection redesign or more hardware/process sharding; it must not be attempted by weakening structured visibility grouping, cache/digest verification, subscription revisions, or committed-state delivery.

## Changes retained

### Immediate committed invalidation

- `server/internal/server/ws.go` delivers the first authoritative PostgreSQL trigger observation after a 1ms micro-batch, rather than imposing the former fixed 75ms debounce. Declared write sets still wait for the committed trigger when necessary.
- `server/internal/server/subscriptions.go` runs an idle shared subscription immediately. Only changes arriving during an active rerun can be coalesced.
- Commit IDs, trigger revisions, and row/table details are still deduplicated and ordered. PostgreSQL notifications remain the authority, so no uncommitted result is propagated.

### Safe shared execution

- Structured visibility plans compute a revisioned fingerprint before a subscription joins a shared group. `ShareResultFrom` remains available for compatible queries that project fields from one canonical source.
- Whagons task grids share only when Gonvex proves that every visibility input is equal. Missing or invalid visibility context fails closed to an identity-specific execution.
- `gonvex/core_extras.go` gives `taskResources.listTaskLogs` the same exact task-visibility fingerprint and replaces a tenant-wide task-log scan with indexed `taskId` reads. `gonvex/shared_tasks_regression_test.go` verifies it does not fall back to permission-only sharing.

An equal visibility key means the query's complete visibility inputs are equal, not merely that two users have the same role. Results are never reused across unmatched keys or different audiences.

### Capability-gated delta transport

- `server/internal/server/subscriptions.go` produces keyed array/page patches, compact order deltas, and atomic object-collection patches when they are materially smaller than full results.
- `packages/protocol/src/index.ts`, `packages/client/src/index.ts`, and `cmd/gonvex-load/runner.go` negotiate and apply the new frame types with revision/base checks.
- A client lacking a capability receives the full `query.result`. A revision mismatch also falls back/resynchronizes rather than applying a patch against unknown state. Digest verification remains unchanged.

### Physical delivery efficiency

- Identical query messages for multiple subscriptions on one connection use capability-gated `query.fanout` frames.
- 32 workers perform physical WebSocket writes before expensive logical telemetry accounting. A 64-worker A/B regressed p95 and was rejected.
- Shared groups are bounded at 5,000 listeners, which shortens disjoint connection sweeps without changing the query result or audience.
- Query-result batching and a commit-wide delivery barrier were tested and removed because they either added latency or coupled fast subscriptions to unrelated slow groups.

### Precise no-op behavior

- Unchanged invalidations no longer emit `query.progress` and do not advance the server revision. The next real patch therefore continues to name exactly the revision held by the client.
- Initial/cache revalidation retains progress semantics. No visible row change can be suppressed because suppression requires the full semantic result hash to match.
- Auth/user writes and declared-table handling were made idempotent/trigger-aware in earlier iterations, reducing the ramp's users-table amplification while retaining actual membership/identity changes.
- The final uncached Whagons suite also caught an unrelated fallback ownership drift: `gonvex/bulk.go` no longer omits `slaPolicies` from `bulk.allReferenceData` recovery results. The isolated load tenant contains zero rows in that table, so this post-certification correctness closure adds only an empty setup key and cannot affect task mutation propagation or the reported TTLU distribution. The corrected bundle was pushed to the tuned runtime.

## Correctness evidence

The optimization boundary was intentionally conservative:

1. **No missed visible updates.** Trigger table/row details, declared dependency predicates, result hashing, and patch revision checks remain active. A semantic result change always produces a result or supported patch.
2. **No cross-identity leakage.** Permission sharing is used only on explicitly permission-scoped functions. User-sensitive task functions require an exact structured visibility fingerprint and fail closed.
3. **No weakened digest verification.** Full results and all patch families preserve cache revision/digest checks; unsupported or stale clients receive/resynchronize with full state.
4. **Committed state only.** The runtime waits for PostgreSQL's post-commit trigger notification before propagating authoritative table changes. The rejected commit barrier experiment was removed; immediate means immediately after committed notification, never before commit.

## Iteration summary

The full detail is preserved in `tmp/goal-iterations.md`. The progression was:

- Iterations 1–20: instrumentation, immediate post-commit invalidation, dependency precision, visibility-safe result sharing, trigger/auth de-amplification, and initial fanout controls. Full p95 reached 284.92ms.
- Iterations 21–24: connection grouping, fanout frames, incremental task snapshots, and first keyed patches. Short probes approached 100ms but did not hold at full duration.
- Iterations 25–29: order deltas and atomic object patches eliminated repeated large payloads; corrected profile-variable contamination; 5k groups and immediate/32-worker delivery became the candidate.
- Iteration 30: GOGC=100 short gate passed at 63.02ms, but a full run reached 207.36ms as tasks grew from 200 to 600.
- Iterations 31–32: larger DB admission and commit batching improved isolated samples but were insufficient or operationally inferior.
- Iterations 33–35: exact task-log sharing/indexing and delivery-free unchanged invalidations reduced hard-state p95 to 120.95ms in a short probe.
- Iterations 36–37: 64 workers and compression both regressed and were rejected.
- Iteration 38: fresh contractual full certification reached the final 182.48ms across-commit p95 with every operational gate green.
- Iteration 39: corrected the `slaPolicies` fallback ownership drift exposed by an uncached final suite; the load tenant's table is empty, so measured mutation TTLU is unchanged.

## Remaining risks and production rollout

- The p99/max tail (234.48/627.97ms across commits) remains material. Production should alert separately on p95 and p99, result bytes, DB pool waits, and per-query delivery duration.
- Task-grid result and patch cost grows with the workspace's live task population. A future sub-100ms project should start with projection/materialized-view design, tighter client windows, or process-level audience sharding—not weaker visibility reuse.
- Roll out `query.fanout`, order deltas, and object patches behind their existing capabilities. Canary legacy clients to verify full-result fallback before broad enablement.
- Keep GOGC=100, 12/8 DB admission, 5k groups, 32 delivery workers, immediate delivery, and compression disabled as the certified starting point. The 16/12 DB A/B was only modestly faster; 24/16 had already been unstable.
- Re-run the full profile with production-like network distance and realistic workspace-size distributions. This certification is specifically local loopback and the documented 200-to-600-task workload.
