TTLU (Time To Last User) is the number that decides whether the app feels real-time: the delay from a mutation committing — someone clicks "change status" — until the last subscribed client's UI reflects it. Not the average client. The last one.

Verdict. The 200 ms product ceiling is met at full scale with margin (p95 182.48 ms across commits; create 187.23 ms, update 178.32 ms). The stricter 100 ms stretch goal was not reached. What remains is a workload-size-dependent floor in database reads, result construction and physical fan-out — not a fixed delay, not GC, not queueing; each of those was eliminated and measured. Crossing 100 ms needs an application-level data/projection redesign or process sharding, and must not be bought by weakening visibility partitioning, digest verification, subscription revisions, or committed-state-only delivery.

What actually changed, and why it worked

Six mechanisms did the work. Each is stated as the problem it removed — that is why the latency fell.

1 · Fixed delay windows → immediate committed delivery

Problem: the pipeline imposed a 75 ms change-batch debounce, a 50 ms pre-run coalesce and a 150 ms cooldown on every update, busy or idle — a ~275 ms floor before a rerun even started, mathematically incompatible with a 200 ms target. Fix: the authoritative post-commit trigger observation flushes immediately with a 1 ms micro-batch; idle groups execute at once and coalescing applies only while a storm is actually in progress. Why it worked: it deleted a constant from every measurement. It also exposed everything behind it — which is why iteration 1 didn't look like a win yet.

2 · Re-running everything → precise, committed invalidation

Problem: one tasks.update declares 21 written tables; that declaration was merged with the precise Postgres trigger data and flattened to "broad", so nearly every subscription in the tenant re-ran. In production, 76% of reruns returned byte-identical results — full query cost, no new information. Fix: per-table precision survives the merge; the trigger's observed tables become authoritative when the tenant listener is healthy (declared writes stay as the fail-safe superset); exact foreign-key, task-ID and caller-ID predicates prune further; unchanged results now emit nothing at all and don't advance revisions. Why it worked: the cheapest query is the one that never runs. Unrelated task inserts stopped waking note/log/view subscriptions; the final run skips 91 tables per propagating commit.

3 · One execution per user → visibility-fingerprint sharing

Problem: 30 users watching the same workspace ran the same expensive query 30 times, because results can legally differ per user, so the runtime keyed executions by user ID. Fix: ShareByVisibility / ShareResultFrom — the app computes an exact fingerprint of what a caller can actually see; identical fingerprint means provably identical results, so one execution serves the whole set, and its serialization and patch templates are reused too. Any uncertainty fails closed to per-identity execution. Why it worked: it broke the link between "how many people are watching" and "how much work a change costs" — the property that makes 1,000 users viable. Iteration 9 alone: 1,020 ms → 53 ms on the probe.

4 · Full results on the wire → delta transport

Problem: every update reshipped whole result sets; one probe moved 4.44 GB. Fix: capability-gated keyed-array, page, order and atomic object patches; stable row order is omitted rather than resent; identical payloads addressed to many subscriptions on one socket collapse into a single query.fanout frame. Legacy clients still get full results; a revision mismatch resynchronizes. Why it worked: 4.44 GB → 402 MB → 36 MB of physical payload. Less serialization, less socket time, less client parse — all three sit directly in the last user's path.

5 · Unbounded goroutines → bounded, measured concurrency

Problem: a broad change spawned ~1,000 concurrent rerun goroutines that stampeded a 20-connection database budget; 300+ queries in flight, 6.6 cumulative hours of pool waits in one run. Fix: a bounded rerun dispatcher and a 32-worker physical delivery pool, with a 5,000-listener cap per shared group so sweeps stay short and concurrent. Why it worked: queue wait went to zero and stayed there. Counter-intuitively the best database setting was fewer connections (12 total / 8 per pool) — 24/16 caused Postgres backend resets, and more concurrency bought contention, not throughput.

6 · O(tenant) handlers → SQL that uses indexes

Problem: most query handlers loaded entire tenant tables into Go and filtered in memory. A query that takes 1 s cannot propagate in 200 ms no matter how good the pipeline is — its floor is its own runtime. Fix: pushed the work into indexed SQL — GROUP BY aggregates, DISTINCT/ EXISTS id-lists, watermark joins, keyset pagination — plus the missing indexes, with old-vs-new result-equality tests. Why it worked: it removed the per-execution term from the whole equation. Measured at el-rey scale (160 workspaces, 50k tasks, 150k notes):

Why 100 ms was not reached

The tail is now dominated by three things that scale with the size of the data itself: the database read, constructing the result, and physically writing it to the last of ~730 relevant sockets. The evidence that it is not anything else:

  • Not queueing — rerun queue wait and depth were zero for the whole certification.
  • Not GC — stop-the-world components stayed under 2 ms at GOGC=100; the long concurrent mark phases are not global pauses.
  • Not the generator — the load tool peaked at 0.8 CPU cores and 389 MB, with no socket errors.
  • Not fixed delays — every debounce/coalesce/cooldown was removed or made adaptive and re-measured.
  • Size-dependent — latency rose measurably as the create mix grew the tenant from 200 to 600 tasks inside a single run.

Getting under 100 ms from here is an application data-shape problem (precomputed/narrower task projections so the payload stops growing with the tenant) or a horizontal one (sharding connections across processes) — not another knob on this pipeline.

Invariants that were never traded for speed. Delivery reflects committed state only — propagating before commit would occasionally show every user a change that then rolls back. A subscription never skips an update that affects its visible rows; any uncertainty (unhealthy listener, missing metadata, ambiguous scope) falls back to delivering. Visibility sharing fails closed to per-identity execution. Digest verification, subscription revisions and cache scoping are unchanged.

How the measurement itself is trustworthy

The end-to-end leg is measured on the server clock only: commit → the receiving client's acknowledgement arriving back at the server. Client clock skew cannot distort it, and it is a strict upper bound on the real user-visible delay — it includes one extra network hop the user never waits for. Four iterations were thrown out entirely rather than reported: missing commit correlation, cross-run ID collisions, trace output blocking a stdout pipe, and a workload where a stale variable override concentrated every create onto all 1,700 connections instead of the contract's ~730. Numbers from those runs are excluded here.
